# Milestone v1.0: PipesBot OpenClaw Channel Plugin

**Status:** SHIPPED 2026-02-18
**Phases:** 1-4
**Total Plans:** 6

## Overview

This roadmap delivers a WhatsApp channel plugin for OpenClaw in four phases following the data flow direction: scaffold the plugin so it loads into the gateway, establish a reliable WebSocket transport to PipesBot, handle all inbound WhatsApp message types, then complete the loop with outbound replies and delivery status. Each phase produces artifacts the next phase depends on, with the two highest-risk components (reconnection and dead connection detection) front-loaded in Phase 2.

## Milestone Summary

**Key Decisions:**

- Custom WS client over @pipes-bot/plugin (tighter OpenClaw lifecycle integration) — Good
- User-scoped pk_ keys only (simpler auth model, covers primary use case) — Good
- WebSocket-only replies, no REST fallback (simpler architecture) — Good
- All media types supported inbound (WhatsApp users send all types) — Good
- Unscoped package name `pipes-bot-channel` to match manifest id — Good
- `noEmit: true` in tsconfig (jiti handles runtime, tsc type-check only) — Good
- dispatchReplyWithBufferedBlockDispatcher (IRC pattern, no typing API) — Good
- No gateway property on ChannelPlugin (prevents lifecycle conflict) — Good

**Issues Resolved:**

- authFailed not reset on stop() (fixed in quick task 001)
- pongTimer overwritten without clearing (fixed in quick task 001)

**Issues Deferred:**

- PipesBot WebSocket close codes not fully documented (deferred to integration testing)

**Technical Debt Incurred:**

- pendingReplies Map not cleared on stop() (by design, lazy TTL eviction)
